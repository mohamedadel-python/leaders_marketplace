## ROUTES_API
- GET /my/vendor/profile (owner only; staff -> 403): store, contact, masked payout account, change form, history.
- POST /my/vendor/profile/bank-change (owner, csrf, multipart): bank_name, account_holder, account_number, proof file (PDF/image, size limit = vendor_document_max_mb). Success: redirect /my/vendor/profile?requested=1. Error: page re-rendered with message.

## UAT
1. Owner: /my/vendor/profile > fill form + proof > Request change. Expect: pending banner, history row, security email queued to the owner (always, even if all notifications are off).
2. Try a second request: the form is hidden / refused while one is pending.
3. Finance/manager: Marketplace > Operations > Payout Account Changes > open > Approve: res.partner.bank created, vendor's payout account replaced, owner emailed (if the switch is on). Or fill Reject reason > Reject.
4. With a pending request, Settlements > Mark Paid raises an error; after review it works. Settlement form and vendor finance table show the payout account (masked in the portal).

## LIMITATIONS
- Security mail goes to the vendor owner user(s) with an email only; if none, a chatter note is posted on the request.
- Portal owners cannot download the proof; only back-office sees it. No IBAN checksum validation.
- Old bank account is kept (not archived) after approval.
- The payout journal entry only carries the masked account in its `ref`; accounts unchanged.

## DECISIONS
- Security mail is non-switchable: `leaders.notification.notify(..., force=True)` skips the settings check; only the requested mail uses it. It shows only the last 4 characters of the account.
- Portal vendor groups have no ACL on the model; routes use sudo after the owner check.
- `_ensure_vendor_bank_account` sets the payout account only when empty, so a later application approval never overrides an approved change.
