## ACCOUNTING (shipping fee)
Fee = min(return_shipping_fee, refund_amount), stored at request time in `shipping_fee_deducted` when switch on, reason.customer_pays_shipping and resolution is refund. `refund_amount`, `commission_refund`, `vendor_deduction`, order `refunded_amount`, commission audit lines, wallet `return` transaction, vendor credit note are UNCHANGED: the vendor bears the goods value exactly as before. Refund entry (`post_return_refund_entry`): debit side unchanged (escrow, or vendor payable + commission income); credit receivable = refund - fee, plus credit fee income (`fee_income_account_id`, else the commission income account) = fee. The customer refund payment (residual of the receivable line) is therefore the net amount. If the customer had not paid, the reconcile leaves the fee (plus unreturned goods) on their receivable. Tests prove balanced entries, receivable 0 after the paid refund posts, escrow 0 and payable == wallet unsettled.
## EXCHANGE
Allowed for storable, non-delivery lines; refused at request time when the vendor's owned stock at the source location is below the quantity. When the goods are received (`_on_goods_received`) `_process_exchange` creates, per source group, a replacement group (`is_replacement`, same source location/type) with its own delivery from the vendor's stock to the customer (owner vendor, moves without `leaders_vendor_line_id`), confirms and reserves it, and sets the return to `exchanged`. No refund entry, credit note, commission, wallet line, invoice or earning; ledger unchanged. The vendor ships the replacement with the existing ship flow (FBM portal ship form / FBL warehouse validation); replacement groups are ignored by the vendor order state machine so the order state never moves. Quantities: `qty_delivered` untouched (moves not linked to the line), `qty_returned` does not count exchanged, and `_qty_returnable` does not count exchanged returns (the customer holds the same quantity again, so a defective replacement can be returned once more; it is not returnable twice for the same unit).
If the stock has vanished by the time goods arrive (practically only if reservations changed), it falls back to refund (resolution set to refund, chatter message) instead of blocking the receipt.

## LIMITATIONS
- Exchange keeps the same product/qty/price by construction (no variant swap). The replacement shipment appears as an extra shipment on the vendor/customer order pages (no per-item list; its lines are not vendor order lines).
- Fee is informational in FBM + COD returns (the vendor refunds the customer in cash; no receivable exists): nothing is booked for it.
- The vendor credit note still shows the full goods value (it is the vendor's document); the customer refund is lower by the fee.
- Disputes have no detail page (they link to the order page's conversation). No new emails.
- Arabic strings need the coordinator's i18n regeneration.
## DECISIONS
- Fee is a separate stored deduction (not folded into `refund_amount`) so commission, wallet, credit note and vendor deduction stay untouched; the marketplace keeps it as fee income (simplest consistent booking).
- Replacement is a group flagged `is_replacement` (spec) but with no vendor lines, filtered out of the order-state logic instead of touching every group consumer.
- Photos are attachments served through ownership-checked routes (portal users have no ACL on the model); SVG refused.
- Filter chips are applied in Python on the customer's own records (small lists), same pattern as vendor pages.
