## SETTINGS (Settings > Marketplace, visible when COD is allowed; all default off)
- `leaders_marketplace.cod_max_amount` Float, 0 = no limit (company currency; order total incl. delivery/tax). Above it the COD button is replaced by a warning message, /shop/payment/cod refuses.
- `leaders_marketplace.cod_require_otp` Boolean, default False. On: phone + code required before /shop/payment/cod accepts.
- `leaders_marketplace.cod_refusal_block_count` Integer, 0 = off. COD hidden (no message) for a customer with count >= N.

## ROUTES_API
- POST `/shop/payment/cod/otp/send` (public, csrf) form `phone`; redirects to `/shop/payment?lm_cod=sent|error`. Refuses above the limit / blocked customer; 60 s between codes, max 5 codes per order per hour.
- POST `/shop/payment/cod/otp/verify` (public, csrf) form `phone`, `code`; redirects `?lm_cod=verified|wrong|error`. 6 digits, valid 5 min, 5 wrong attempts then locked (ask a new code). Success sets `sale.order.leaders_cod_phone_verified`.
- `/shop/payment/cod` now calls `order._leaders_cod_check_allowed()` (limit, block, OTP verified) -> UserError.
- POST `/my/vendor/fulfillment/<group_id>/refused` (vendor owner/staff, csrf) form `reason` (optional). FBM groups of the vendor only; redirects to the order page (`?error=` on refusal).
- Python API: `leaders.cod.otp._leaders_send_otp(phone, code, partner=None) -> bool`; `leaders.fulfillment.group.action_customer_refused(reason=None, by=None)`; `sale.order._leaders_cod_availability() -> (bool, msg)`; `res.partner._leaders_cod_blocked()`, `.action_reset_cod_refusals()`.

## UAT
1. Settings: set COD max amount 500; customer with a cart of 800 at /shop/payment sees the warning instead of the COD button; below 500 the button shows.
2. Tick "COD Phone Verification": /shop/payment shows phone + Send code + code entry; without SMS the code is logged at INFO in the server log (fallback, on purpose) and emailed via the mail queue; enter it: "Phone number verified" and the COD button appears. Wrong code 5 times locks it; wait 60 s to request a new one.
3. FBM COD: vendor ships (tracking), order page shows "Customer refused" (only while shipped): order + group cancelled (reason "Refused at delivery"), stock back in the vendor location, no wallet/earning, customer counter +1.
4. FBL COD: manager opens the vendor order > Fulfillment tab > "Customer refused" on the shipped group; a receipt "Refused at delivery" stays open: warehouse validates it when the parcel is back (stock returns, owner = vendor).
5. Set "Block COD After Refusals" to 2: after two refusals that customer no longer sees COD. Contact form (managers) shows the counter with "Reset COD refusals".

## LIMITATIONS
- Refusal is only allowed from `shipped` (not `delivery_reported`: once the vendor claimed delivery a refusal is a dispute).
- If the vendor order has another group that is delivered/delivery_reported the refusal is refused (use a return); other shipped groups of the same vendor order are refused together.
- FBM refusal validates the return receipt at once (vendor's own responsibility); FBL leaves the receipt for the warehouse (backend only, buttons for the marketplace manager group; warehouse users have no ACL on the group form).
- Only the vendor order is cancelled; the company part of a mixed COD checkout (company sale order) is untouched.
- Message on the payment page when the customer is blocked: none (option just disappears). Not a substitute for SMS delivery guarantees: without `sms` the code goes by email only if the customer has an email.
- No refusal email notification.

## DECISIONS
- Refusal reuses `VendorOrder.action_cancel` via context `leaders_cod_refusal` (bypasses only the "already shipped" check and the generic customer mail); so commission lines, vendor invoice, collection reversal (if any; COD has none before delivery) and picking cancellation stay shared. Return receipt is created BEFORE cancel so the cancel path does not cancel it.
- cancelled_by_type = customer as specified; the counter is incremented by the refusal action itself, never derived from cancelled_by_type, so A2 cancellations (before shipping) never count. Consequence: refused orders are excluded from KPIs like other customer cancellations.
- OTP sending uses `sms.sms` (Odoo 18 has no `sms.api` model) only when installed; on gateway error it falls back too.
- OTP flow is plain http forms + redirects (no JS, no assets) and works RTL/LTR/mobile with Bootstrap classes.
