Conventions

  • JSON in, JSON out, Content-Type: application/json on every request body (a JSON object).
  • No envelope. A success body is the resource itself.
  • camelCase names, durations in integer seconds, optional fields omitted, except user.avatar which is null when unset.
  • Protected endpoints read Authorization: Bearer <accessToken>. Missing, expired, forged or malformed is 401 session_expired.
  • Every response carries Cache-Control: no-store. Send every request with credentials: "include".

Errors are a non-2xx status with this body. code is a stable snake_case string the UI branches on; message is English, for developers and logs.

{ "code": "invalid_credentials", "message": "Email or password is wrong." }

// 422 validation_error adds per-field messages keyed by request field:
{ "code": "validation_error", "message": "Validation failed.", "fields": { "email": "Invalid email" } }

Two tokens, two homes. The access token never touches storage; the refresh token never touches JavaScript.

CORS. The backend answers with Access-Control-Allow-Origin: <your origin> (exact, never *) and Access-Control-Allow-Credentials: true, only for the origin configured on the server. Preflight OPTIONS returns 204 with Allow-Methods: POST, OPTIONS and Allow-Headers: Content-Type, Authorization.

SessionResponse

interface SessionResponse {
  accessToken: string;      // JWT
  tokenType: "Bearer";
  expiresIn: number;        // seconds until accessToken expires; 900, never below 120
  user: {
    id: string;             // numeric id as a string
    name: string;
    email: string;          // lower-cased
    avatar: string | null;  // absolute URL, null when the user has no picture
  };
}

The client computes expiresAt = now + expiresIn and refreshes 60 seconds early.

No body. The browser sends the refresh_token cookie by itself. On success a new refresh cookie is set (rotation) and the old one stops working; presenting an already-rotated token revokes the whole login chain. A 401 is normal and means "not signed in": both cookies are cleared in that response.

Flows end to end

Register or login

  1. Form posts to /auth/register or /auth/login.
  2. Client keeps accessToken and user in memory; the browser stores the two cookies.
  3. Redirect to the page the user came from, or the home page.

Page reload

  1. Middleware sees spark_session and lets the protected page render.
  2. App calls /auth/refresh and rebuilds the session.
  3. On 401 the client clears its state and the user is signed out.

Expiring access token

  1. Before any authenticated request the client checks expiry.
  2. Within 60 seconds of expiring, call /auth/refresh first.
  3. Run one refresh at a time and share its result: a concurrent second refresh with the old cookie counts as token reuse and signs the user out.

Forgot password

  1. /auth/password/forgot, then the app opens the code screen.
  2. /auth/password/verify returns resetToken.
  3. /auth/password/reset, then go to login.

Notes

  • Limits. Register 10/min per IP. Login 30/min per IP and 10/min per email. Refresh 60/min per IP. Forgot 10/min per IP and 3 per 10 min per email. Verify 30/min, reset 10/min per IP. These numbers are the backend's choice and can change.
  • Serialize refreshes. Two simultaneous /auth/refresh calls race and the second revokes the session. Use one in-flight promise.
  • The JWT works on the auth endpoints for now. The existing marketplace routes (/api/v1/vendor/…) use API keys. Tell us which other endpoints the client will call with this Bearer token.
  • Environment. We need your exact frontend origin (for CORS), HTTPS in every environment (cookies are Secure), and a shared parent domain if any (for Domain=). Email delivery depends on the server's outgoing mail setup.
  • Frontend test fixtures (staging only). Set the system parameter leaders_marketplace.auth_fixtures to True and the user demo@spark-fu.example is created on its first /auth/password/forgot.
